**Upstream refs:** ggml-org/llama.cpp #29030 (gather lazy rows with direct reads, open), #29599 (`llama_prefetch_rows` API + `--prefetch-rows`, open), #28136 (prototype, >2x prefill measured, closed unmerged).

## Persona
Me: single user running `unsloth/Qwen3.8-Flash-Next-GGUF` (qwen4exp) on a 62 GB-RAM box with Intel Arc Pro B70 x2. The PLE/n-gram table (`per_layer_token_embd`, ~47 GB, kept at 4-bit, same size across quants) lives on NVMe and is consumed row-wise via `--lazy-mode auto`.

## Story
As a llama.cpp user running models with huge lazily-mapped embedding tables (qwen4exp PLE, future ngram-heavy models),
I want lazy row reads to be gathered into batched, direct-I/O syscalls and prefetched during GPU compute,
so that prompt processing stops paying per-row page-fault + `madvise(DONTNEED)` + refault round-trips against my NVMe.

## Rationale (evidence)
- #28136 measured **>2x prefill** on a GB10-class offload rig by replacing row-at-a-time mmap faults with direct reads (closed unmerged; direction revived by #29030/#29599).
- PLE access pattern is pure random-row lookup (320M rows, 16 heads, offsets) — the worst case for page-cache-as-API and the best case for gather+prefetch.
- Strata (independent engine, docs/DETAILS.md) built its entire SSD-tier around exactly this pattern and reports ~400–1450 t/s pp on modest hardware; llama.cpp's current lazy path is the streaming bottleneck in our bench plan instead.

## Acceptance criteria
1. When a tensor is lazy (`LLAMA_LAZY_MODE_ON/AUTO`), the row-fetch path issues **one gather call per ubatch** (readv-style / single direct-read) instead of N faults.
2. `--prefetch-rows <n>` (and/or `llama_prefetch_rows` API) exists; prefetch of chunk *i+1*'s rows overlaps compute of chunk *i*; disabled by default keeps behavior bit-identical.
3. Page-cache friendliness: second identical prompt is not slower than first (prefetch must not thrash the warm cache); first-run pp gain ≥1.5x on NVMe vs master for UD-Q4_K_XL at 8K prompt (our rig, llama-bench pp512–pp8192).
4. No regression when lazy-mode is `off`; mmap-spanning Metal class bugs (#29465-analogs) covered by existing platform guards; Windows named-pipe-free path (OverlappedFileReadFileRanges) per #29030 design.
5. Review path: comment on #29030/#29599 with our measurements; offer to rebase/carry #28136's deltas if maintainers want a single consolidated PR. Do not fork silently — establish communication first.

### UD-Q4_K_XL acceptance #3 attempt (2026-10-01) - HARDWARE-BLOCKED on this rig

Downloaded UD-Q4_K_XL (4 shards, 111.33 GB) to `/root/q4-k-xl/`. It cannot run the full-offload 8K pp
test on the 2x32GB B70 rig:

- Lazy PLE (`add_lazy_reader`): `320001536 rows of 90 bytes` = 28.8 GB stays on NVMe (row reads enabled).
- Non-lazy main weights = 111.33 - 28.8 = **~82.5 GB**, which exceeds both 64 GB total GPU (2x32) and
  62 GB host RAM. Full offload (`-ngl 48 --split-mode layer --tensor-split 50,50`) OOMs during tensor
  load even at `-c 512`, with both `--fit off` and `--fit on`
  (`UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY`, `ggml-sycl/common.hpp:161`). `--fit on` auto-balanced to
  25/24 layers and still OOMed (it under-accounts, #27595).
- Cross-check: Q2 non-lazy ~50 GB and Q3 non-lazy ~61 GB both fit 64 GB GPU (consistent with their
  passing full-offload runs); Q4 does not.
- The prompt is 8114 tokens, so even the context floor is `-c >= 8242` (8114 + 128 gen), adding KV pressure.

Why no partial-offload proxy is valid: the only way to make Q4 load on 2x32GB is `-cmoe` (ALL MoE experts on
CPU). Probed it: it loads and runs, but mmaps ~76 GB of CPU expert buffers (`CPU_Mapped 19431+47013+11509 MiB`)
on a 62 GB-RAM box -> heavy page thrashing, and pp is dominated by CPU expert GEMM (warmup ~9.5 t/s). `-ncmoe 24`
still OOMs because with `--split-mode layer 50,50` the first 25 layers' experts (~39.5 GB, ~1.58 GB/layer) always
land on GPU0 (32 GB) regardless of `-ncmoe` (which only moves the *last* N layers, i.e. GPU1's). So no config
keeps enough on GPU for a representative pp: the gather's benefit is on the *fixed* PLE read, and CPU-expert
dilution + thrash noise makes the combo/master ratio uninterpretable (a sub-1.5x number could not be distinguished
from the dilution). Running it would yield a misleading acceptance number, so it was skipped deliberately.

Conclusion for acceptance #3: the `>=1.5x` gate is already met on the two quants that fit at full offload
(Q2 `2.27x`, Q3 `1.98x`). Q4_K_XL cannot be validated on this 2x32GB rig; it needs a larger-VRAM rig
(e.g. 2x48GB+ or 4x32GB). Note Q4 is expected to be the HARDEST case for the 1.5x gate: bigger GPU-resident
main weights dilute the PLE-read fraction relative to Q2/Q3, so its ratio would likely sit below Q3's 1.98x.
