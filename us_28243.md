### 2026-09-30 — Bottleneck linkage: the 0.81x is a known MoE bottleneck, not a rig property (user reframe)
- **Reframe (user)**: "MTP hurts current rig -> we have a bottleneck somewhere; retest once it is identified and fixed. It is not a new direction; the bottleneck is likely one of the identified user stories."
- **Mechanism**: MTP round (n_max=2) = 2 cheap draft steps (1 MTP block each, but each runs the shared **dense 200K-vocab output projection**) + 1 target **verify** step (3 tokens x 48 MoE blocks). When the MoE path is launch/bandwidth-bound, the verify step scales ~linearly with token count (V ~ 3x a single decode step), so MTP's total cost (2D + V) exceeds 3 plain decode steps -> net loss. The draft's dense output projection adds a fixed per-draft cost on top.
- **Primary suspect = us_29245 (SYCL grouped-MoE XMX GEMM)**: documents the B70 SYCL MoE as launch/bandwidth-bound (effective ~150 GB/s vs ~608 GB/s HW peak; "thousands of small ESIMD/scalar expert ops per layer"). Batching routed experts into XMX grouped GEMMs cuts the verify-step launch overhead (V < 3x) — exactly what MTP needs to pay for itself.
- **Secondary suspect = us_25356 (MUL_MAT_ID batch cliff)**: explicitly names us_28243 as a downstream consumer ("the cliff would masquerade as 'MTP stopped helping'"). Our n_max=2 (3 verify rows) sits **under** the rows>8 cliff, so it likely did NOT trigger in this run; it would bite at n_max>=6 or multi-slot.
- **Action**: criterion 4 is **deferred, not failed**. Re-run the both-GPU MTP A/B (same Q2_K_XL, -ngl 48 layer-split) once us_29245 (and us_25356) land on the test branch. Do NOT conclude "MTP is a 2x B70 rig property" before that retest. research.md §4/§8 updated to match.

### Parked follow-up (2026-10-01) — can we make 64K MTP work on 2x32GB?
**Status: PARKED (low priority, behind us_otgen).** 32K MTP already meets criterion 4, so 64K is a stretch goal, not a blocker. But the q4_0 failure is a *different* error than the q8_0 OOM, so it is worth one focused investigation to decide whether it is a genuine capacity wall or a fixable software limit.

Observed:
- q8_0 KV: OOM in `llama_kv_cache::clear` (VRAM: target KV 446 MiB/GPU + draft f16 KV 56 MiB/GPU + draft compute buffers + 90GB weights > 2x32GB at 70K).
- q4_0 KV: loads fine, but dies during processing with `UR_RESULT_ERROR_OUT_OF_RESOURCES` at `ggml-sycl/cpy.cpp:1426` (cross-GPU copy path). No-draft 64K runs fine at both quants, so the wall is specific to the draft's second context at 70K.

Investigation angles (in risk order):
1. **Characterize the q4_0 `cpy.cpp:1426` failure.** Is it a real 2x32GB capacity wall (target+draft simply cannot co-reside at 70K) or a fixable software limit (a single oversized cross-device memcpy / buffer / kernel resource)? Read `ggml-sycl/cpy.cpp:1426` and the surrounding `dev2dev_memcpy` path; confirm which tensor copy overflows and whether it is one large transfer.
2. **Chunked/split cross-device copy.** If the copy is one large transfer, chunking it (or routing it through a smaller staging buffer) may clear the resource ceiling. Check `GGML_SYCL_DEV2DEV_MEMCPY` (0 SYCL peer / 1 Level Zero / 2 host-forward) variants.
3. **Draft placement.** The MTP draft context is currently layer-split across both GPUs like the target. Try pinning the draft to a single GPU (or a much smaller split) to shrink the cross-GPU copy footprint and the draft's per-GPU compute buffers.
